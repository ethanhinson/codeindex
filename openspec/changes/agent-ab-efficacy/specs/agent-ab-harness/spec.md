## ADDED Requirements

### Requirement: Task generation with arm-neutral ground truth

The system SHALL generate a fixed, versioned task set (`bench/agent_ab/tasks/tasks.json`)
containing comprehension and localization tasks over the pinned repositories,
where every task's ground truth is computable by script without using codeindex.

Each task record SHALL contain: `id`, `type` (`comprehension` | `localization`),
`repo` (name matching `bench/repos.json`), `prompt` (the exact text given to the
agent), `ground_truth` (see scenarios), and `meta` (symbol or issue/PR numbers,
selection filters applied).

#### Scenario: Comprehension task generation

- **WHEN** the task builder runs against a pinned repository
- **THEN** it selects symbols by a scripted, seeded rule: parse definition
  candidates via ripgrep patterns (reuse `bench/token_bench.py` `extract_symbols`),
  keep names with length ≥ 4 defined in non-test files, and sample a published
  mix of ~70% symbols with exactly one definition and 2–20 referencing files and
  ~30% "hot" symbols with multiple definitions or > 20 referencing files
- **AND** each task's prompt is: `In the repository at <abs path>, where is
  '<symbol>' defined? Give every definition as file:line. Then list every file
  (path relative to the repo root) that references '<symbol>'. Answer with a
  'DEFINITIONS:' section of file:line entries and a 'FILES:' section of paths,
  nothing else. Base every claim on evidence from the repository — do not answer
  from memory.`
- **AND** ground truth is generated by ripgrep only: definitions = file:line of
  lines matching the language definition regex for the symbol; referencing
  files = `rg -w -l <symbol>` output

#### Scenario: Localization task generation

- **WHEN** the task builder queries the GitHub API for a pinned repository
- **THEN** it selects closed issues whose closing merged PR changed 1–10 `.go`
  files (excluding `vendor/`), where ≥ 60% of those files exist at the pinned
  commit, using the issue's timeline/linked-PR data and the PR files endpoint
- **AND** each task's prompt embeds the issue title and body verbatim plus:
  `Identify which files in the repository at <abs path> would need to change to
  fix this issue. Answer with a 'FILES:' section listing repo-relative paths,
  nothing else. Base your answer on evidence from the repository.`
- **AND** ground truth is the PR's changed `.go` file list filtered to files
  existing at the pinned commit
- **AND** the API responses used are cached to disk so task generation is
  reproducible offline

#### Scenario: Task set is pinned and balanced

- **WHEN** the full task set is emitted
- **THEN** it contains at least 20 tasks with both types represented across at
  least two repositories (default: gin and prometheus; kubernetes excluded in
  v1), the RNG seed recorded, and the file committed to the repository before
  the full run

### Requirement: Two-arm isolated execution

The system SHALL run every task in two arms — control (A) and treatment (B) —
via the headless `claude` CLI, with identical configuration except the
treatment's appended system prompt, and with per-run isolation.

#### Scenario: Arm configuration parity

- **WHEN** a task runs in either arm
- **THEN** both arms use the same model, `--max-turns` cap, allowed tools
  (`Bash,Read,Grep,Glob` — no Edit/Write), working directory (the pinned repo
  clone), and prompt
- **AND** arm B additionally receives `--append-system-prompt` with the
  contents of `bench/agent_ab/prompts/arm_b_tools.md`: documentation of the
  codeindex binary at its ABSOLUTE path (outside the repo tree), its `query`
  output format, when to prefer it over Grep/Read, and exactly one worked
  example
- **AND** arm A's environment contains no mention of codeindex, and the binary
  is not discoverable inside the repo tree

#### Scenario: Index freshness for arm B

- **WHEN** the harness starts a session against a repository
- **THEN** it runs `codeindex build <repo>` once before any arm-B run and
  records the build time separately (amortized one-time cost, reported but not
  charged to any single task)

#### Scenario: Per-run isolation and reset

- **WHEN** any run completes
- **THEN** the harness restores the repo (`git checkout -- .`) and verifies
  `git status --porcelain` is clean before the next run
- **AND** runs are executed serially per repository clone (no concurrent runs
  sharing a working tree)
- **AND** task×arm×rep order is randomized with a recorded seed

#### Scenario: Smoke mode is mandatory before the full matrix

- **WHEN** the harness is invoked without an explicit `--full` flag
- **THEN** it runs at most 2 tasks × both arms × 1 rep, prints the parsed
  metrics and grades, and instructs the operator to inspect transcripts before
  running `--full`

### Requirement: Metric capture per run

The system SHALL record, for every (task, arm, rep) run, a result row containing
tokens, cost, behavior counts, grading inputs, and provenance.

#### Scenario: Result row contents

- **WHEN** a run completes
- **THEN** the result row records: task id, arm, rep, model, `claude` CLI
  version, start/end wall time, `num_turns`, input tokens, output tokens, cache
  read/creation tokens, `total_cost_usd`, tool-call counts by tool name, the
  count of Bash invocations of the codeindex binary (`codeindex_calls`), the
  agent's final answer text, the path to the archived full transcript
  (stream-json), and an error/timeout flag
- **AND** rows are appended to `bench/agent_ab/results/runs.jsonl` immediately
  after each run (crash-safe; a re-run resumes by skipping completed
  (task, arm, rep) keys)

#### Scenario: Budget guard

- **WHEN** the summed `total_cost_usd` across recorded rows exceeds the
  configured `--budget-usd`
- **THEN** the harness stops launching new runs and reports partial results

### Requirement: Arm-blind script grading

The system SHALL grade every run's final answer against the task's ground truth
by script, without knowledge of the arm, producing precision, recall, F1, and a
success boolean.

#### Scenario: Comprehension grading

- **WHEN** a comprehension answer is graded
- **THEN** the grader extracts `file:line` pairs from the DEFINITIONS section
  and repo-relative paths from the FILES section (tolerating markdown
  decoration and absolute-path prefixes, normalizing to repo-relative)
- **AND** definitions score: a claimed definition matches ground truth if the
  path matches and the line is within ±2 of truth
- **AND** files score: set F1 against the ground-truth referencing-file set
- **AND** the task F1 is the mean of the definitions F1 and files F1, and
  `success` = (task F1 ≥ 0.5)

#### Scenario: Localization grading

- **WHEN** a localization answer is graded
- **THEN** the grader computes set precision/recall/F1 of the answer's FILES
  list against the PR-derived ground-truth file set, and `success` = (F1 ≥ 0.5)

#### Scenario: Malformed answers score zero, not error

- **WHEN** an answer contains no parseable section
- **THEN** the run is graded F1 = 0, success = false, and flagged `unparseable`
  (reported separately so a formatting failure is distinguishable from a wrong
  answer)

### Requirement: Paired analysis and report

The system SHALL produce an aggregate report computing paired per-task
statistics between arms, both intent-to-treat and per-protocol, against the
pre-registered thresholds.

#### Scenario: Paired statistics

- **WHEN** the report runs over `runs.jsonl`
- **THEN** for each task it computes per-arm medians over reps of total tokens
  (input+output), cost, and turns, then the paired per-task deltas and
  percentage reductions (B vs A)
- **AND** reports the median paired token reduction with a 95% bootstrap
  confidence interval (≥ 5,000 resamples over tasks), the win rate (% of tasks
  where B used fewer tokens), success rates per arm with their delta, and
  median turns per arm

#### Scenario: Adoption and per-protocol view

- **WHEN** the report runs
- **THEN** it reports adoption = % of arm-B runs with `codeindex_calls ≥ 1`,
  and repeats the paired analysis restricted to tasks where adoption held in
  every arm-B rep (per-protocol)
- **AND** a large intent-to-treat vs per-protocol gap is called out explicitly
  as a discoverability finding, not a tool failure

#### Scenario: Pre-registered verdict

- **WHEN** the report completes on a full run
- **THEN** it evaluates the recorded GREEN/YELLOW/RED thresholds from the task
  file header verbatim and prints the verdict with the supporting numbers
- **AND** writes `bench/agent_ab/results/report.md` containing: methodology
  summary, headline verdict, the paired table (per task: tokens A, tokens B,
  delta %, success A/B, codeindex calls), adoption analysis, cost totals, and
  every caveat that applied (unparseable runs, timeouts, dropped tasks)

### Requirement: Reproducibility

The system SHALL make the experiment repeatable: pinned repos, pinned task set,
recorded seeds, archived transcripts, and a re-runnable analysis.

#### Scenario: Re-running analysis without re-running agents

- **WHEN** `report.py` is invoked on an existing `runs.jsonl`
- **THEN** it reproduces the full report deterministically (bootstrap seeded)
  without any agent execution

#### Scenario: Provenance in every artifact

- **WHEN** any result or report is written
- **THEN** it embeds the repo pins (name + commit), task-file hash, model,
  `claude` CLI version, codeindex binary build hash (`git rev-parse HEAD` of
  this repo at build time), and all seeds
