Does a call-graph index actually help coding agents?

A paired A/B study on real repositories. Short answer: yes, on structural code questions — and the effect is a property of the task, not the repo or the language.

codeindex is a call-graph index (Go, TS/JS, Python, PHP): it answers who-calls-X, what-X-calls, and blast-radius questions with complete, always-fresh path:line output. The question this page answers is narrower and more honest than "is it good": when you give a coding agent this tool, does it spend fewer tokens and get more answers right — and for which kinds of task?

Method

Each task is run twice under identical conditions: arm A (control — the agent has grep/read only) and arm B (the agent additionally has codeindex). Same model, same prompts, paired and repeated. Tasks are mined from real open-source repositories (ground truth from ripgrep and the call graph, never from the index under test). The control arm is hard-isolated from the index via an environment guard, so it cannot leak.

Tasks fall into types that stress different retrieval strategies — from "which functions call X" (structural) to "where is the onboarding flow" (comprehension).

Result 1 — the index wins big on structural tasks, and it's a routing signal

Not everything benefits. The value is concentrated in tasks that are genuinely graph-shaped (caller attribution, occurrences, blast radius). For comprehension / locate tasks, plain grep is already the right tool and the index is roughly a wash — occasionally worse. That distinction is the whole point: a good policy should route, not reach for the index every time.

Result 2 — the effect is structural: it survives the Go→PHP boundary

The obvious worry: maybe these wins are memorized quirks of the Go repos the tool was tuned on. To test that, the full task set was reproduced on laravel/framework (PHP) — a different language where static call resolution is genuinely harder (duck-typed dispatch produces ambiguous edges). If the routing signal is structural, its sign should hold across the boundary.

On the two hardest buckets the index doesn't just cut cost — it improves correctness (edit impact +13 points, occurrences +25 points of success rate). "Use the index for structural questions; it's a wash for comprehension" is a property of the task type, not the repository or the language.

A note on honesty

The first PHP edit-impact run (small sample) showed the index making the agent faster but less correct — a tempting story about ambiguous PHP edges. A larger 30-per-arm re-run refuted it: the effect was noise from a handful of runs, and at scale edit impact is a clean win (+60% cheaper, +13 points more correct). The lesson recorded in the findings: don't build a mechanism narrative on a 12-row cell.

Result 3 — you don't even need a router: over-retrieval hits the ceiling

Result 1 said the policy should route. The natural next question: route with what? A trained classifier (local embeddings + logistic regression) picking the right tool per task scored only 70% end-to-end — its errors concentrate exactly in the caller-shaped tasks where the index matters most.

The measured answer is simpler: don't decide. Each retrieval costs milliseconds, so run all of them — callers, symbol search, and word-boundary grep — and emit one union answer. That deterministic pipeline scores 100% success, F1 0.95–0.99, per-task identical to the best per-question tool, on all three languages tested (Go, PHP, TypeScript). No agent in the loop, no model, no routing — just structure plus cheap glue. It ships as a product verb, codeindex nav, and the four common multi-hop trajectories (impact, where-tested, rename-radius, dead-code) fall to the same treatment.

Why this matters

A large fraction of a coding agent's spend goes to navigation — locating the relevant code — not reasoning about it. This project set out expecting to train a small routing policy for that layer. The measurements kept refusing: the classifier router lost to running everything; cheap query-formulation gates lost to a local embedding+structure hybrid; at every gate where a model might have earned its way in, deterministic retrieval plus cheap glue matched or beat it. So the conclusion is stronger than "the index helps": for navigation-shaped questions, the expensive model can be kept out of the loop entirely, and invoked only where actual reasoning is required. What remains genuinely open for a model is narrow and named: query reformulation on the weakest semantic-search repos, and the trust-vs-verify call on [ambiguous] edges.
